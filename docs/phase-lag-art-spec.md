# 《迟相 / Phase Lag》美术资产规格

## 目的

本文档用于决定绘制和采购素材时的尺寸、锚点、动画名与替换边界。碰撞、关卡坐标和玩法逻辑独立于正式美术；替换素材时优先改 SpriteFrames、纹理和视觉子节点，不移动碰撞体来迁就画面。主角与敌人的实际交付勾选表见 `docs/phase-lag-character-art-requirements.md`。

两只机器人占位已经删除。当前陆衡使用 Ansimuz `Cyberpunk Detective`，星遥使用 LuizMelo `Huntress`；两者都是可替换的人形 CC0 过渡素材，不代表最终自绘定稿。

环境、门、UI、音乐和音效已接入可用来源素材；主角与四类敌人仍是可替换过渡素材。来源、许可证与处理记录见 `docs/phase-lag-asset-sources.md`。

## 一、视觉方向

### 总体风格

- 现代高清像素风，世界以 `32px` 视觉格组织。
- 角色轮廓清晰、动作夸张，避免在分屏缩小时依赖细小面部信息。
- 场景使用有限色板，但关键交互物必须比背景高一个明度或饱和度层级。
- 玩法世界与 HUD 保持硬边像素语言；菜单只轻量统一，不强行做低分辨率像素排版。
- 画面不依赖纯黑描边解决一切，优先用冷暖环境色、轮廓光和局部高亮分层。

### 双空间对照

| 层级 | 陆衡空间 | 星遥空间 |
| --- | --- | --- |
| 情绪 | 冷、静、事故后的废墟 | 暖、急、事故正在发生 |
| 主色 | 冷青、灰绿、深蓝灰 | 暖橙、警报红、焦褐 |
| 高亮 | 青绿电流、淡白设备灯 | 橙黄火花、红色警报灯 |
| 运动 | 尘埃慢漂、远处结构轻晃 | 火花、烟、警报扫光、压力泄漏 |
| 完整度 | 缺板、断线、腐蚀、空洞 | 结构完整但过热、变形、受冲击 |

建议基础色可从当前场景色板起步，再由正式美术统一调整：

- 冷暗：`#07151A`、`#0A1E23`、`#1B393A`、`#2D4F4B`。
- 冷亮：`#48D7C7`、`#9AFAE2`。
- 暖暗：`#150D11`、`#301715`、`#57271C`、`#753923`。
- 暖亮：`#F6682F`、`#FFCD65`、`#D03026`。
- Boss 中性金属：`#0D1319`、`#6F9197`。

正式色板不要求逐色照搬，但冷暖两侧的明度结构必须同构，让玩家能快速识别“这是同一个位置的另一个时间/空间状态”。

## 二、画布与镜头

- 项目基准：`1920×1080`。
- 单侧世界：`1920×704`。
- 世界格：`32×32px`，一间完整房间为 `60×22` 格。
- 地面碰撞顶边：`y=640`；底部 64px 为地面厚度。
- 玩家出生基准：约 `(150, 592)`。
- 相位锚基准：约 `(1660, 574)`。
- 房间出口基准：约 `(1810, 568)`。
- 主视角显示完整 `704px` 高玩法带；辅助视角裁切为 `352px` 高。
- 任何关键机关、敌人动作和跳跃落点都应放在 `y=352–640` 的辅助视角可读区。

### 分屏检查

每套正式素材至少在以下窗口检查一次：

- `1280×720`：最小主要验收尺寸，检查文字、轮廓和辅助视角可读性。
- `1920×1080`：设计基准。
- 仅支持 `16:9`：以 `1920×1080` 为基准，`1280×720` 用于同比例缩放检查；不为超宽屏单独扩展画布。
- 合并画面必须填满完整 `16:9` 画布。使用等比放大和水平裁切，不纵向拉伸，不保留上下黑边。

Godot 使用 `canvas_items + expand`，SubViewport 按布局改变高度，Camera2D 保持统一水平缩放。布局动画期间允许短暂非整数缩放，不要求严格 pixel-perfect 锁帧。

## 三、当前角色素材合同

| 角色 | 当前来源 | 原生帧 | 资源入口 | 显示参数 |
| --- | --- | --- | --- | --- |
| 陆衡 | Ansimuz `Cyberpunk Detective` | 常规动作 `32×32px`，倒地帧 `46×32px` | `resources/phase_lag/characters/lu_heng_visual.tres` | `scale=5x`，offset `(0,-34)` |
| 星遥 | LuizMelo `Huntress` | `150×150px` | `resources/phase_lag/characters/xing_yao_visual.tres` | `scale=2.5x`，offset `(0,-34)` |

两份 `.tres` 保持统一运行时动画合同。通用动作包括 `idle`、`run`、`jump`、`fall`、`dash`、`hurt`、`collapse`、`revive`、`defend`、`primary`、`secondary`、`dodge`；陆衡额外使用 `aim`、`grab`、`rotate`，星遥额外使用 `slash_1`、`slash_2`、`slash_3`、`charge`、`heavy`、`counter`、`air_slash`、`dive`。

当前过渡包缺少的专属动作通过最接近的现有帧映射，确保选中、旋转、战斗和受击状态都有可见角色反馈。以后自绘时只替换两份 `.tres` 的 SpriteFrames，并保留动画名、视觉原点和碰撞边界。

## 四、角色规格

### 通用

- 陆衡原生帧较小，当前使用 `5x`；星遥原生帧带透明留白，当前使用 `2.5x`。两者以脚底锚点对齐，而不是强求相同原生画布。
- 最终可读视觉高度目标为 `160–180px`，允许范围 `150–190px`；现有过渡素材尚未稳定达到该目标，后续自绘角色不能缩回原来的小人比例。
- 当前角色碰撞为 Capsule，约 `110px` 宽、`180px` 高，不随服装和武器摆动改变。
- 陆衡交互距离约 `280px`；正式工具和动作轮廓应与该范围匹配。
- 自绘动画可使用更大的原生帧并把 `sprite_scale` 调回接近 `1.0`，但脚底、视觉中心和碰撞包络必须保持一致。
- 左右方向由 `AnimatedSprite2D.flip_h` 处理，默认绘制朝右。
- 大幅武器或工具可以超出 64px 主体，但尽量保留在 96px 帧内。
- 如果视觉中心改变，调整 `PhaseCharacterVisualConfig.sprite_offset`，不要移动碰撞体。

### 陆衡

#### 轮廓要求

- 纤细、收束、重心偏后，和星遥的前倾动作形成反差。
- 磁束检修枪必须在辅助视角中仍能辨认，枪口至少有 4–6px 的高亮块。
- 冷色主体不应与冷背景融在一起，可使用浅色肩线、面罩或工具光强调轮廓。

#### 必需动画名

| 动画 | 最低建议帧数 | 关键内容 |
| --- | --- | --- |
| `idle` | 4 | 小幅呼吸、工具灯慢闪。 |
| `run` | 6 | 工具稳定，身体不要像战斗冲刺。 |
| `jump` | 2 | 起跳收腿。 |
| `fall` | 2 | 下落与落地前准备。 |
| `dash` | 4 | 地面短冲，主体压低。 |
| `aim` | 3 | 抬枪并锁定实体管线或磁力物体。 |
| `grab` | 4 | 磁束建立、物体被吸起。 |
| `rotate` | 4 | 手腕或枪口产生 90° 旋转反馈。 |
| `hurt` | 3 | 清楚的受击方向。 |
| `collapse` | 5 | 倒地且不与死亡敌人混淆。 |
| `revive` | 5 | 从相位锚恢复。 |

`primary`、`secondary`、`dodge`、`defend` 是通用运行合同，可在 SpriteFrames 中复用 `grab`、`rotate`、`dash`、`aim` 的帧。

#### 独立 VFX

- 磁束枪本体建议约 `32×16px`，可包含在动作帧中，也可作为独立 Sprite2D。
- 磁束为独立 Line2D/粒子 VFX，不要烘焙进所有角色帧。
- 抓取中颜色：冷青；成功吸附时转为短促金色确认。

### 星遥

#### 轮廓要求

- 动作前倾、重心积极，长刀形成清晰的大对角线。
- 救援长刀应像工业工具而不是细剑：厚背、切割齿或热切割结构均可。
- 暖色角色要用暗色内轮廓与背景警报红分离。

#### 必需动画名

| 动画 | 最低建议帧数 | 关键内容 |
| --- | --- | --- |
| `idle` | 4 | 大方、松弛，但随时能行动。 |
| `run` | 6 | 长刀随身体形成稳定节奏。 |
| `jump` | 2 | 起跳。 |
| `fall` | 2 | 下落。 |
| `dash` | 4 | 地面/空中共用的高速位移轮廓。 |
| `slash_1` | 4 | 最快横斩。 |
| `slash_2` | 4 | 改变方向或高度，避免三刀同形。 |
| `slash_3` | 5 | 明确收束和击退感。 |
| `charge` | 4 | 起手前 `0.18s` 必须读得出反击架势。 |
| `heavy` | 6 | 蓄力释放、强破甲、明显后摇。 |
| `counter` | 5 | 格挡转反击，一眼区别于普通重击。 |
| `air_slash` | 4 | 水平追击。 |
| `dive` | 5 | 向下砸落和落地冲击。 |
| `hurt` | 3 | 受击。 |
| `collapse` | 5 | 倒地。 |
| `revive` | 5 | 恢复。 |

救援长刀可直接画入动作帧。斩击轨迹、命中火花和落地冲击使用独立 VFX，以便调整命中时序而不重画角色。

## 五、敌人与 Boss

### 相位寄生体

- 当前场景使用 Ansimuz 地行异形的后五格行走帧，`crawl`、`leap`、`attach`、`hit`、`dead` 随 FSM 切换；这是统一风格过渡素材，不是最终寄生体设计。
- 建议帧画布：`64×64px`；主体约 `48×48px`。
- 碰撞主体当前约 `40px` 高、`36px` 宽。
- 必需动画：`crawl`、`leap`、`attach`、`hit`、`death`。
- `attach` 必须清楚表现正在影响哪个设备，连接触须或相位环应指向目标。
- 死亡后要保留短暂相位残渣，方便玩家看懂 `destroyed` 已经发出但尚未抵达另一侧。

### 舰载无人机

- 当前场景使用 Ansimuz `ship-unit-with-thrusts.png` 的后七格推进动画；这是过渡素材，最终图必须补齐追踪、预警、俯冲、受击和失控状态。
- 建议帧画布：`128×96px`；机体约 `96×64px`。
- 机体质心必须稳定，代码负责上下悬浮，不要把大幅上下位移烘焙进帧。
- 必需动画：`hover`、`track`、`warn`、`dash`、`shoot`、`hit`、`death`。
- 攻击预警应由炮口、翼片或推进器姿态表达，外部方框只作辅助。

### 设施守卫机

- 当前场景使用 Ansimuz biped 七帧图集作为过渡素材，并随 `patrol`、`windup`、`charge`、`attack`、`stagger`、`corpse` 状态切换。
- 动画帧画布：`128×128px`。
- 主体约 `96px` 高；碰撞约 `72×92px`。
- 必需动画：`walk`、`shield`、`charge_start`、`charge`、`impact`、`attack`、`stagger`、`shutdown`、`corpse`。
- 供电护甲必须是独立清晰的外层轮廓；断电预演不能和真正断电混淆。
- 尸体状态要有稳定底面，视觉上能解释为什么可以压住压力板。

### 相位猎手

- 当前场景使用 Ansimuz tank 图集作为过渡素材，并保留可拆甲片、陷阱与双色核心 authored 层。
- 动画帧画布：`192×192px`。
- 主体约 `128px`，原点居中。
- 正式扩展建议使用 SpriteFrames 或 AnimationPlayer 补齐状态动画。
- 必需动画：`idle`、`chase`、`attack`、`break_charge`、`teleport`、`stun`、`core_open`、`defeat`。

#### Boss 可拆视觉层

- `PixelBody`：唯一可移动本体。
- `WarningHalo`：跃迁和破防预警。
- `PhaseShards`：跃迁裂解碎片。
- `ArmorPlates`：第一轮三层甲片，必须能逐层独立裂解和破碎。
- `TrapClamps`：第二轮三个共享符号的束缚轮廓。
- `FinalCore/CoreCold`：陆衡供电半边。
- `FinalCore/CoreWarm`：星遥重击半边。
- `CoreHitArea`：逻辑命中区，不随夸张特效缩放。

Boss 传送残像不可攻击。残像透明度和颗粒密度可以变化，但轮廓不能比真实本体更实。

## 六、电路与机关素材

### 电路零件

- 每块 `32×32px`，透明背景。
- 零度方向按当前 Resource 定义绘制：右为输出主方向。
- 端口中心落在实体模块四边的连接点，线宽建议 `4–6px`。
- 程序会旋转零件，不要为四个方向制作四份独立逻辑资源。
- 带电状态通过材质、叠加光或替换色表现，不要求另做一整套贴图。

| 零件 | 零度端口 |
| --- | --- |
| 直线 | 左、右 |
| 弯线 | 上、右 |
| 三通 | 上、左、右 |
| 计时器/反向/记忆 | 左入、右出 |
| 双路开关 | 上与左输入、右输出 |
| 发电机 | 右输出 |
| 纠缠输出 | 左输入 |

计时器的 `1/3/6` 必须在 `1280×720` 辅助视角中可辨认。除数字外再使用节奏色或刻度差异，避免色盲玩家只能靠颜色区分。

### 实体因果管线

- 一组 authored 管线设施建议占地约 `480×320px`，但插槽、导管和总闸必须依房间空间单独摆放。
- 不再使用固定逻辑网格、选择框、全屏 modal 或独立小游戏背景。
- 固定模块与可移动模块需要明显不同；可移动模块使用弱描边，靠近和手持时增强。
- `HeldPreview` 直接显示手持零件纹理、插口和 `0/90/180/270°` 方向，设施外框不能遮挡预览。
- 连接线必须能追踪到门、平台、护盾或 relay；不要只靠文字或 link id 表达对应关系。
- 操作不依赖独立 focus camera，正常分屏内也必须能读懂插槽和模块朝向。

### 设备建议画布

| 设备 | 建议画布 | 当前碰撞/用途 |
| --- | --- | --- |
| 门 | `64×256px` 或沿用 atlas `64×128px` 再缩放 | 约 `42×224px` 阻挡体。 |
| 平台 | `192×64px` | 约 `176×28px` 可站立面。 |
| 激光 | `64×224px` | 中央约 `18×184px` 伤害区。 |
| 护盾发生器 | `64×256px` | 护盾约 `30×224px`。 |
| 压力板 | `96×32px` | 需有压下、保持和释放三个状态。 |
| 房间复位闸 | `64×96px` | 和实体管线总闸外形明显不同。 |
| 过载脉冲闸 | 核心约 `96×96px`，整组设备建议 `640×352px` | 核心、双电容、母线、状态灯、局部光和放电粒子分层。 |
| 磁力物体 | `48×48px` | 电池、保险丝、配重块使用不同轮廓。 |
| 磁力插槽 | `48×48px` | 显示兼容类型和占用状态。 |

门已使用 Ganamoda 同包的完整关闭/打开门组；其他机关继续保留 authored VisualGroup、碰撞与状态层。替换外观时只改对应 `.tscn` 的视觉子节点，不恢复通用 placeholder atlas，也不得在来源门图上叠加临时手画护栏、裂纹、霓虹框或无来源装饰层。

## 七、背景与图层

每侧背景建议拆成以下层，而不是把正式场景永久烘焙为一张图：

1. 最远层：星空、设施外壳、结构剪影。
2. 中景层：管线、舱壁、设备组、破损层。
3. 设施交互层：实体管线、插槽、闸刀和明确的设备连接走向。
4. 玩法层：地面、平台、门、敌人、磁力物体。
5. 前景层：烟、管线边缘、玻璃反光，不能遮挡角色和目标预演。

当前每侧房间使用 Ansimuz 素材拆分为远景、设施墙和前景遮挡层，并在 authored scene 中做冷暖改色。关卡坐标仍保持：

- 地面顶边 `y=640`。
- 第一处装饰平台顶边约 `y=520`。
- 第二处装饰平台顶边约 `y=456`。
- 两侧结构位置尽量同构，差异来自事故时间和损坏状态。

背景继续在对应 authored room `.tscn` 中组合，不在运行时生成，也不恢复旧单图背景。

### 第二章“断电窗口”房间套件

- 陆衡侧电容站占地约 `608×344px`，交互核心位于约 `(480,548)`；正式素材应拆分背板、左右电容、顶部母线、三段延迟单元、双菱形纠缠标记和前景交互闸。
- 星遥侧护甲供能站占地约 `632×248px`，中心约 `(1100,344)`；与陆衡侧使用同一双菱形标记，但改用暖橙事故色和更完整的设施状态。
- 冲锋场两根撞柱中心约为 `(640,592)` 与 `(1560,592)`，碰撞尺寸 `72×96px`；高架中心约 `(1100,464)`，碰撞尺寸 `640×32px`。正式图块可以扩大支架外观，但不能侵入碰撞通道或遮挡守卫预警环。
- 两侧同构的是供能关系和标记，不要求背景损坏完全镜像。冷侧强调废弃检修站，暖侧强调仍在工作的护甲供能场。

### 第二章“回传”房间套件

- 陆衡侧实体管线中心约 `(366,484)`，升降台中心约 `(620,654)`，升起后位移 `-192px`；高架顶边 `y=448`，检修隔墙从地面延伸至 `y=464`。正式支架可以更宽，但必须保留平台与高架的水平接缝。
- 陆衡终门中心约 `(1480,528)`；门楣使用双菱形回传标记，右侧走廊必须保留角色、相位锚和出口的清晰轮廓。
- 星遥战区门中心约 `(600,528)`，门楣封住跳跃绕行；守卫初始中心约 `(1040,580)`，压板约 `(1320,634)`，两者水平距离 `280px`。
- 压板右侧挡块中心约 `(1450,584)`，碰撞 `72×112px`。挡块既截停残骸又可被星遥跳过，正式素材需要明显的受力面和朝向压板的地面箭头。
- 压板设备与陆衡终门共享双菱形符号；不要用文字或 link id 表示它们的对应关系。

## 八、VFX 与可访问性

### RemoteArrivalVfx

- `power_changed`：局部扫描线、断续电流、抵达放电。
- `form_changed`：目标形态残影向真实位置收束。
- `destroyed`：像素边缘剥落和碎片预演，抵达时才真正消失。
- 多部件设备或敌人使用 `CanvasGroup` 时，保留材质的 `sample_canvas_group = true`；单独 Sprite/Polygon 保持关闭。替换 VisualGroup 时不要把两种采样模式混用。
- 预演颜色来自发送侧，目标物本体状态仍由接收侧色板决定。

### PhaseSeamVfx

- 常态裂缝核心 `4–8px`。
- 跨界波约 `0.35s`；低闪烁模式约 `0.52s` 且更低亮度。
- 第五章零延迟时不应持续高亮全屏，只保留低强度相位干涉后消失。

### 低闪烁模式

- 禁止快速全屏白闪、连续高对比反相和大面积频闪。
- 允许稳定轮廓、慢速缩放、残影、颜色渐变和较长包络。
- 所有关键机制必须在低闪烁模式下仍可仅凭形状和运动读懂。

## 九、立绘、CG 与 UI

### 立绘

- 每人至少 4 种表情：中性、警觉/愤怒、放松/玩笑、脆弱/告白。
- 建议画布 `512×512px`，透明背景。
- 身体朝向和光源应能对应冷暖空间；终章可制作同一光源下的同步版本。

### 终章 CG

- `1920×1080px`。
- 两人第一次同处一画面，但构图中保留相位缝或时间戳校正痕迹。
- 告白后新信号出现时，不再使用人物大特写，留出空间让“迟到仍会抵达”的主题落下。

### HUD

- 只常驻章节、两人生命和模式信息；房间目标不使用常驻文字面板。
- 生命槽为 authored 图形：陆衡两格、星遥三格。脚本只切换填充层显隐，不使用 `◆/◇` 等字体符号。
- 控制提示短暂出现，不长期占据世界画面。
- 不显示 Boss 阶段说明、任务计数、中央事件列表或精确倒计时。
- 字体需要完整中文字符集；像素世界可配像素标题字体，正文优先保证可读性。

## 十一、替换流程

1. 角色优先更新 `resources/phase_lag/characters/lu_heng_visual.tres` 与 `xing_yao_visual.tres`。
2. 保留必需动画名；允许每个动画使用独立贴图、多帧 SpriteFrames 或 AnimationPlayer。
3. 调整视觉偏移时只改 `sprite_offset` / `sprite_scale`，不要移动玩家碰撞。
4. 设备在对应 `.tscn` 中替换 VisualGroup，保留脚本、碰撞、RemoteArrivalVfx 和持久化组。
5. Boss 替换 `PixelBody` 或补充 AnimationPlayer 时，保留甲片、陷阱、双色核心和 CoreHitArea 的逻辑节点。
6. 纹理导入使用 nearest，关闭 mipmap。
7. 运行 Godot 项目导入、脚本解析和主场景短启动。
8. 最后人工检查动作有效帧是否与命中区、因果抵达和 Boss 预警同步。
